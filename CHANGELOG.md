# Changelog

All notable changes to this module. It follows [Semantic Versioning](https://semver.org); until 1.0, a minor version may change the API.

## v0.7.0 (unreleased)

Needs acp-go v0.5.0. Breaking: `claudeacp.Main` takes a `Config`.

- **Breaking:** `claudeacp.Main(cfg Config) error`, as `codexacp.Main` takes one: a caller can set `Spawn` (or `Log`, `CLIPath`, `ConfigDir`) and keep Main's signal handling. Main fills a nil `Log` (stderr) and an empty `CLIPath` (`$CLAUDE_CODE_EXECUTABLE`), and always sets `SharedGroup`. Callers of `Main()` pass `claudeacp.Config{}`.
- `claudeacp`: `Main` waits for SIGTERM and SIGINT with `signal.NotifyContext`. The log line on a signal now reads `signal="terminated signal received"` where it read `signal=terminated`.
- `claudeacp`: a new session's (or fork's) available commands wait for its answer through acp-go's `AfterResponse`, not by matching the bytes the connection writes, so a change to acp-go's encoding can't break it.
- `claudeagent`: `Exec` runs claude through acp-go's `process` package, the code `acp.Start` runs agents with. Two behaviour changes:
  - On Windows, a claude started without `SharedGroup` gets a console process group and a job object of its own, so `Wait` (once claude exits) and `Signal(os.Kill)` end what it started (MCP servers, hooks), as a process group already does on Unix. Before, nothing it started was ended there. `Main` sets `SharedGroup`, so it is unaffected.
  - On Unix, `Signal` reaches claude alone when its group is gone, where it failed.
- `claudeagent`: a failure to make claude's pipes reads `claudeagent: start <path>: ...`, as a failed start does.
- Tests: shared helpers for a turn's stop reason, loads, an opened session, line lists and claude's empty control answer.

## v0.6.1 (2026-11-21)

- Builds on acp-go v0.4.1: a call whose context has ended is never sent, a response with neither result nor error fails its call, a request reusing a live id is refused, and requests wait while 64 answers are unread.
- Security: a JSON `Options.Settings` (a session's `settings` object in `claudeacp`) no longer goes on claude's command line, where any local user could read it, an env block's tokens included, with `ps`. It goes in a 0600 file in a private 0700 temp folder, named by `--settings` and removed once claude exits (or the start fails); claude may read it again while it runs, so it stays until then. A `Spawner` gets that path in `Spec.Args`; `claudetest.Fake.Settings` returns what the file held. A settings path is passed as before.
- Docs: `claudeacp.Config.Log` says claude's stderr lines go to it too (at Info, cut at 1 KiB, rate-limited), and may quote a prompt or a token, as the README says; it said the log never held one.
- `claudeagent`, on Windows: claude is found on PATH as `claude.exe` (or another extension `PATHEXT` names), without the execute bits Windows files don't have, and a `CLIPath` with forward slashes (`C:/tools/claude.exe`) is taken as a path, not looked up. Every session failed with "claude isn't on PATH" unless `CLAUDE_CODE_EXECUTABLE` was a backslash path.

## v0.6.0 (2026-11-20)

- `claudeacp`: a background subagent's totals reach the client. Its Agent call ends at once (`toolResponse.status` `async_launched`), and claude tells what the subagent used only in its task notification (`usage`), which the agent dropped. They now go as a `tool_call_update` of that Agent call with only `_meta.claudeCode.toolResponse` `{totalTokens, totalToolUseCount, totalDurationMs}`, the names a foreground subagent's own response has them under, so a client reads them where it already does. `session/load` replays them from the `<usage>` of claude's `<task-notification>`, a subagent's subagent's too. See the README's "Background subagents".

## v0.5.0 (2026-11-17)

- `claudeacp`: a background command's task reaches the client. A Bash call with `run_in_background` completes at once, but claude runs its command as a task (`local_bash`) whose start and end the agent dropped, so a client never heard that the command ended. Each change of the task now goes to every client as a `tool_call_update` of the Bash call with `_meta.claudeCode.task` `{id, type, status, outputFile?, summary?, endTime?}`: `running` as claude starts it, then claude's word for its end (`completed`; `failed`, also when killed from outside; `killed` then `stopped` for claude's `TaskStop`), in order with the turn's other updates. The call's own status stays `completed`. It is an update of the call, not an update type of its own, because the call is what a client already shows for the command and `_meta.claudeCode` is where it reads claude's facts on a call; a client that doesn't read it sees nothing new, so no capability is needed. claude-agent-acp sends these tasks only to JetBrains AIR (`async_task_*`). See the README's "Background commands".
- `claudeacp`: `session/load` replays a background command's end where the history has it: claude's `<task-notification>` of it, or claude's `TaskStop` of it. A command an open session's claude still runs replays as running.
- `claudeagent`: `TaskUpdated`'s `Patch` has `EndTime`, claude's `end_time` (milliseconds since the epoch).

## v0.4.0 (2026-11-14)

The fixes from a whole-code review (115 findings, all of them but one), on acp-go v0.4.0. Breaking: `claudeacp.Main` returns an error, `claudeagent.CancelAsyncMessage` returns whether the message was cancelled, `CompactBoundary.CompactMetadata` is a `*CompactMetadata`, `--mcp-config` is passed a file, and `claudetest.Replay` checks what the client decided.

- `claudeacp`: the effort, fast mode and agent options, and ultracode, follow claude's settings files (the user's, the project's, the local and the managed ones) and a settings file the session names (from its cwd), under the settings the session gives, with a model's own effort (`modelSettings`) first, as claude-agent-acp reads them. An effort change then keeps ultracode a settings file turned on, where claude turned it off.
- `claudeacp`: a load or resume of an open session that sets it up otherwise (its folder, extra folders, MCP servers, system prompt, or `_meta`'s `claudeCode`, `systemPrompt` and `additionalRoots`) closes its claude and resumes it so, in the permission mode it was in, as claude-agent-acp does; claude went on in the old setup, editing the old folder.
- `claudeacp`: a loaded, resumed or forked session with no title is titled from its conversation, its history included: claude made and kept a title from the first prompt after the load alone.
- `claudeacp`: a loaded, resumed or forked session's model option says the model its history last ran on (not claude's `<synthetic>` messages'), which claude resumes it on, as claude-agent-acp reads it; it said the default until the first turn, so picking the default changed nothing.
- `claudeacp`: a prompt's answer has `_meta.quota` as claude-agent-acp's does: `token_count` (the turn's usage) and `model_usage`, a row per model of what the turn's results added to claude's running `modelUsage` (the session's first result gives its own usage under its model).
- `claudeagent/sessions`: `Subagent` has `Name`, `AgentType` and `Description`, from its sidecar. `claudeacp` announces a subagent a SendMessage resumes after a restart with them, as claude-agent-acp does, where it had no title or description.
- `claudeacp`: an ExitPlanMode call is titled `Approve Plan` and a Skill call `Load skill: <skill>`, as claude-agent-acp 0.94 titles them (they said `Plan ready` and `Skill <skill>`).
- `claudeacp`: a fast mode change claude refused says "Claude didn't change fast mode: …", where it said "the fast".
- `claudeacp`: ExitPlanMode's answer is checked against the options the user was shown, not ones worked out again when the answer came: Auto mode picked on a model that lost it meanwhile starts the work accepting edits, where the approval became "The user cancelled."
- `claudeacp`: what a subagent's stream was writing (its last message's text, its tool uses' inputs) is forgotten when the subagent ends, rather than kept until the session closes.
- `claudeacp`: a delete, load, resume or fork of a session that is closing waits for its claude to exit: a delete removed the transcript while claude still wrote it (so the chat came back), and a load ran a second claude on it. A delete is also ordered against a load of the same session.
- `claudeacp`: claude's own messages (`<synthetic>`: an API error, a limit) no longer become the session's model, so `usage_update` names the model that ran and the window is its, not the largest the result names. A failed turn's `errorKind` is its own, not the last turn's that had one. A rate limit's news before any message has counted the context sends no `usage_update`, which showed the session at zero.
- `claudeacp`: a hook-blocked turn says why once. A result's text is shown, for a turn that showed none, only when the model wrote nothing (`output_tokens` 0) and no notice of the turn said it; a notice sent as text counts as text shown, as in claude-agent-acp.
- `claudeacp`: an extension method it doesn't know is answered `Method not found` with `data.method`, as acp-go and claude-agent-acp answer one, where the message named the method and data was empty.
- `claudeacp`: a prompt claude folded into a turn that waits for a steer is answered at the result that names it; it was left unanswered while claude sat idle.
- `claudeacp`: a permission or question the stopped work asks as a cancel comes is denied, never put to the user: the check and the request's opening are one step, so the cancel either withdraws it or comes first.
- `claudeacp`: a session/cancel sent right after a session/prompt cancels it, however soon after; it ran to `end_turn` when the cancel was handled before the prompt's turn was queued (it uses acp-go's `SequenceFromContext`). A cancel's drops and interrupt are written after the user messages of the turns they stop, never before; and the running turn's steers claude hasn't taken are dropped too, where claude ran them after the interrupt as a turn of their own.
- `claudeacp`: withdrawing one prompt (`$/cancel_request`) stops that prompt alone: a queued one is dropped from claude's queue, the running one interrupted; the other prompts go on, where all were cancelled.
- `claudeacp`: a cancel of the turn spares what a background subagent's own foreground subagents ask, as it spares the background subagent's: their requests were withdrawn, so claude was told to deny and interrupt them.
- API change: `claudeacp.Main` returns an error: what broke the connection to the client (logged too), nil when the client went or a signal ended the agent. `claude-acp` exits with 1 on it, where it exited 0. A signal now ends the agent through `Serve`'s ctx; the pipe Main put in front of stdin is gone, as acp-go's Close ends a connection on a blocking stdin.
- Builds on acp-go v0.4.0. `claudeacp`: a Write over an existing empty file shows old text `""` rather than a new file; a tool call with no content says `"content":[]`, as claude-agent-acp does; a subagent that ends with no reason known is sent as acp-go's reasonless idle state; a client's message over the 64 MiB cap is skipped and answered rather than ending the connection.
- The module builds on Windows (`claudeagent/sessions` used Unix-only open flags; claude-tee Unix-only signals). `make check` and CI build and vet it for Windows; the tests still run on macOS and Linux only.
- `claudeagent.Decode` copies the line it is given, so a message's `Raw` no longer changes when the caller reuses its buffer (a `bufio.Scanner`'s, say).
- `claudeagent.ContextCategory` has `Kind` ("used", "free", "buffer", "deferred"), the field claude says to classify a category on, rather than its English name.
- API change: `Session.CancelAsyncMessage` returns `(cancelled bool, err error)`. `cancelled` is false when claude had already taken the message (or folded it into a batch) and will act on it; before, nil said nothing about that.
- `CanUseTool` may return `&Allow{…}` or `&Deny{…}`: a pointer was refused at run time as "no Allow or Deny", so the tool was denied.
- An `Allow`'s `PermissionUpdate` built without `Destination` is sent with `DestinationSession`, and one that lacks what its type uses (`Rules` and `Behavior`, `Mode`, `Directories`) is refused with an error that names it: claude dropped such an update silently, so an "always allow" was never kept.
- `HookFunc`'s doc says hooks fail open: an error or a missed deadline lets the guarded action go ahead. New `HookMatcher.OnFailure` (`HookFailContinue`, `HookFailBlock`) is sent as claude's `onFailure`, so an erroring guard hook can block instead.
- Docs: the package doc has an Environment section that lists what `claudeagent` removes from, sets in and defaults in claude's environment; `Options.Env` points to it.
- With `Options.Spawner` set, `CLIPath` goes to the Spawner as it is (`"claude"` when empty) instead of being looked up on PATH, so a fake or remote Spawner works where claude isn't installed.
- With `Options.Log` set, claude's version is logged from its answer to initialize; no second `claude --version` process runs per session any more, and `CLAUDEAGENT_SKIP_VERSION` is gone.
- New `claudeagent.ErrExitedBeforeInit`: `Start`'s error when claude ends before it answers initialize, whatever its exit code (with the `*ExitError` beside it for a non-zero one). `claudeacp` tells a vanished session by it rather than by the error's text.
- A write to a claude that has exited is `ErrClosed` (wrapping the pipe's error), not a bare "broken pipe"; and `Start` against a claude that exits before initialize can be written still returns `ErrExitedBeforeInit` with the `*ExitError` and its stderr.
- A session closes claude's stdout and stderr once they are read to the end, and its stdin once claude exits, instead of leaving the descriptors to the GC.
- A write with an already-ended ctx (`Send`, `SetModel`…) never reaches claude; before, it did about half the time. A request whose answer came as its ctx ended returns that answer, and isn't withdrawn.
- A write stuck on a claude that stopped reading its stdin no longer holds every other write: requests and `Send` give up as their ctx says while they wait for the write slot, so a close's bounded interrupt gets through to `Close`. Withdrawing a request waits at most 5 s to be written.
- `claudeagent.MCPServer` sends no `"type"` when `Type` is empty (claude refused `""`, so a type-less stdio server from `_meta` was skipped), and keeps a decoded config in the new `Raw`, so the fields it doesn't name (`headersHelper`, `oauth`, `timeout`…) reach claude.
- Security: `Options.MCPServers` no longer go on claude's command line, where any local user could read their env values and HTTP headers (tokens) with `ps`. They go in a 0600 file in a private 0700 temp folder, named by `--mcp-config` and removed once claude has answered initialize (or the start fails, or the session closes). A `Spawner` gets that path in `Spec.Args`; `claudetest.Fake.MCPConfig` returns what it held. A JSON `Options.Settings` still goes on the command line, as its doc now says.
- `sessions.Store.Fork` with `ForkOptions.Cwd` gives the fork's records that cwd, so `List` and `Get` report the fork in its new folder (they reported the source's, and a load from there failed).
- `sessions`: a long path's project folder under another CLI build's hash is taken only when its transcripts record that path as their cwd. The first 200 characters alone matched a sibling deep path's folder, so `List` showed, and `Fork` wrote into, another project's.
- Docs: `sessions.Store.Fork` says the subagents' transcripts aren't copied, so a replay of a fork shows its Agent calls without their subagents.
- New `sessions.Store.Open(ctx, id, cwd)` finds a session once and returns a `*Transcript` with `Messages`, `Subagents`, `QueuedPrompts` and `LastRecord`; a `Subagent` has `Messages` and `QueuedPrompts` of its own. Reading a session with N subagents then runs `git worktree list` once, not 3+2N times, and re-reads no sidecars. `ctx` reaches the git it runs. The `Store` methods are unchanged and work as before.
- `claudeacp`: a Write whose content claude took as `file_text` or `file_content`, and a Bash call whose description came as `command_description`, show that text, as claude-agent-acp shows it.
- `claudeacp`: a Read of an image shows the image and a Read of a PDF a line naming the document, where an empty code block showed; a command's image output shows too. An API server tool's result (web search, web fetch, tool search, code execution) says what it found, where the call had no content.
- `claudeacp`: a tool's result shows the tool's own output where claude gives it (`tool_use_result`), as claude-agent-acp does, live and in a loaded session: a command's output without claude's wrapper for the model (output too long ends with where it was saved), a file read without claude's notes, a web search's hits as `Title (url)` lines, and a subagent's report.
- `claudeacp`: a subagent's report loses claude's frame also when claude's notes come above it (a turn limit, output saved), and its `agentId: … (…)` line also when unframed; a turn limit's note shows as `[Agent stopped at its turn limit — the output below is partial]`. Only a trailing `<usage>` block is cut.
- `claudeacp`: an approved ExitPlanMode call keeps showing the plan, retitled `Exited Plan Mode`, and a Skill call keeps its content, where claude's result text for the model replaced them; a refused plan's reason is unfenced in `rawOutput`.
- `claudeacp`: an Edit's or Write's diffs from claude's response say the line each hunk starts at; a Write over a file whose response has no hunks shows the old text against the new, or says the old was too large to diff, where it showed a new file being created.
- `claudeacp`: each of claude's progress beats for a running tool goes to the client with `_meta.claudeCode.toolResponse` `{elapsedTimeSeconds, subagentType?, subagentRetry?}`, where only the first went, bare; a beat under an id of its own (a heartbeat, a subagent's retries) goes to its parent call. `claudeagent.ToolProgress` has `SubagentType` and `SubagentRetry`.
- `claudeacp`: a tool's result that isn't its output says why under `_meta.claudeCode`, `nonExecutionKind` (`user-rejected`, `permission-rule`, `interrupted`, `cancelled`, `automode-…`) and `userFeedback`, from claude's `tool_result_meta`, as claude-agent-acp does. `claudeagent.User` has `ToolResultMeta`, as claude sent it.
- `claudeacp`: a call claude refused without asking says the rule's reason (`decision_reason`) before claude's message, as claude-agent-acp does; its `toolResponse` leaves out fields claude didn't give, and the call's later result adds claude's text as `rawOutput`.
- `claudeacp`: a compaction's `rawOutput` says trigger `automatic` (else `manual`) as claude-agent-acp does, and leaves out counts claude didn't give, where it said `auto` and 0; a boundary with no facts gives no `rawOutput`.
- `claudeacp`: a failed `/compact` says why once, in its call: claude's copy of the error as a command's output is dropped, and a turn that showed a compaction doesn't show its result's text again, as claude-agent-acp does.
- `claudeacp`: a client that declares `session.compaction` gets ACP's `compaction_update`s for a compaction, as claude-agent-acp sends them, in place of the `Compact conversation` tool call: `in_progress`, then `completed` with the summary from claude's PostCompact hook (its `<summary>`, without the model's analysis), `failed` with the error, or `cancelled` when the turn ends first.
- `claudeacp`: a notice is shaped as claude-agent-acp shapes it: plain text (no `**`, backticks or heading marks), its first line the title and the rest the description, or a generic title when that line is over 256 characters; one per tool use, where claude repeats a tool's progress. - `claudeacp`: a memory recall's read links the memory files it read, and a synthesized one (mode `synthesize`) is titled `Recalled synthesized memory` with the memory's text as its content; `_meta.claudeCode.toolResponse` says the mode, as claude-agent-acp does.

- `claudeacp`: a subagent's TaskCreate, TaskUpdate and TaskList change the session's plan too, live and in a loaded session, as the task list is the session's; they are still shown as the subagent's calls.

- `claudeacp`: without subagent sessions, a subagent that ended and runs again (a SendMessage, a new start, a running update) counts as running: its next end ends the calls that run left open, and a cancel of the turn spares it while it is in the background.

A subagent claude resumes with no new `task_started` (a running `task_updated`, or a SendMessage's result) now ends at that run's end, and its open calls with it; a late `task_started` of an earlier run is ignored.
- `claudeacp`: cancelling a subagent's session also withdraws what the foreground subagents under it ask, as claude stops them with it, so they no longer show running again before they end.
- `claudeacp`: a subagent's tool call whose `tool_call` went on the session (held past the bounds before claude named the subagent) has its later updates go there too, not to the child, so it is no longer left pending on the session.
- `claudeacp`: after `session/resume`, a SendMessage that resumes a subagent from before the restart finds, in the session's history, the call that first started it, which claude sends the run's work under: that work now goes to the subagent's session instead of being held and later sent on the session.
- `claudeacp`: a load ends a foreground subagent whose call's error names a stop (interrupted, stopped, cancelled, killed) as cancelled, as the live session and claude-agent-acp have it, instead of failed with that error.
- `claudeacp`: a replayed user message keeps the user's words as claude-agent-acp does: each marker tag closes only with its own closing tag, an opening tag with no close is the user's text, and a message is shown as the command it ran only when nothing but markers is in it (and the command names itself with a `/` and printed nothing).
- `claudeagent/sessions`: `Subagent` has `Background` (the sidecar's `requestShape` is `background`) and `StoppedByUser`. `claudeacp`'s load uses them: a subagent claude ran in the background unasked is no longer ended by its call's immediate result, and one the user stopped ends cancelled.
- `claudeacp`: a replayed call the history has no result for (claude was stopped while it ran, or the session was forked before its result) ends failed, instead of staying pending; one the live session still runs is left to it.
- `claudeacp`: a load replays a fork child's (`subagent_type: "fork"`) own work alone, without the copy of the launching message and the directive boilerplate its transcript starts with, as claude-agent-acp does: the fork's call no longer stays pending on the session, and its sibling subagents are no longer announced under the fork. A replayed call's result ends only the call of its own transcript.
- `claudeacp`: a load replays a prompt claude took into a running turn (kept only as a `queued_command` attachment) as the user's message where claude took it, under the uuid of the message it came from, as the SDK and claude-agent-acp have it; not a task's end, a meta prompt, or one the transcript also has as a user message.
- `claudeacp`: a load replays a SendMessage's message to a subagent where the subagent's transcript has it delivered (`origin.kind` `coordinator`), before the run it started, as live and as claude-agent-acp replays it; it came after that run's work.
- `claudeacp`: a load of a session that is open already replays its subagents again, as it replays the rest of the history: each is announced, its transcript replays on its session, and its end is its state now (running, requires_action, or how it ended) rather than the history's guess. It keeps the call it runs for.
- `claudeagent/sessions`: `Queued` has `ID` (the attachment's `source_uuid`, else its uuid), `Meta` and `Notification`.
- `claudeagent/claudetest`: `Replay` checks what the client decided, not only a line's kind: a control_request's plain arguments (stop_task's `task_id`, set_model's `model`; not initialize's), a control_response's subtype, the request it answers and a permission's `behavior`, and a user message's content. Ids are compared as the live ones they were mapped to; other fields aren't checked. A test that wrote other text than the recording's, or answered another way, fails now.
- `claudeagent/claudetest`: `Fake.Awaiting` is no longer met by a line the client has just written: a line on its way to the script, or taken by a step that hasn't returned, counts as given, and Awaiting waits for the script's next wait. The fake's `Proc.Stdin` is now a writer of its own that counts lines, not the bare pipe.
- `claude-tee`: a frame's `ms` is taken as the frame is written, so times never go back in a cassette when stdin and stdout lines come together.
- `claude-tee`: a cassette no longer keeps an MCP server's credentials in a `url` (its userinfo, and query parameters named like a key or token) or in its `args` (the values of flags so named, `NAME=value` pairs and `Authorization: …` style headers). A token in a URL's path is still kept: read a cassette before you share it.
- The README no longer calls `claude-acp` a static binary, and shows `CGO_ENABLED=0 go install …` for one on Linux. It and the command's doc say claude's own stderr is logged as claude wrote it (capped), so it may quote a prompt.
- `claudeacp`: a load or fork finds the session's transcript once, with `sessions.Store.Open` under the request's ctx, and the replay reads the subagents and queued prompts from it: `git worktree list` runs once per folder looked in, not 3+2N times for N subagents.

## v0.2.0 (2026-11-05)

- `claudeacp`: a `_session/generateTitle` extension method (`GenerateTitleMethod`) that asks claude for a short title for any text, with its fast model and `persist: false`, so the session keeps its own title. A client titles a message with it, a pinned one say.
- `claudeacp`: replayed tool calls and message chunks are built the way the live stream builds them, so a loaded session shows what the live one did.
- `claudeagent/sessions`: a queued prompt's text and a fork's title are read the way `List` reads them; the chain and a subagent's transcript are walked back the same way; the standard library's `uuid` and `cmp.Or` replace local helpers.
- `claudeagent/claudetest`: the `Step` constructors are in `steps.go`; an expected stdin line is read once, for `Expect` and a cassette's steps alike.
- Internal: a session's open requests are counted by its open set; claude's session is kept on the config rather than behind a one-method interface.

## v0.1.0 (2026-11-05)

The first release.

- `claudeagent`: a client for the claude CLI's stream-JSON control protocol: sessions (`Start`) and one-shot queries (`Query`), typed messages with their raw JSON kept, permissions (`CanUseTool`), hooks, MCP elicitations, and claude's control requests (model, permission mode, interrupt, MCP servers, context usage, file rewind, flag settings).
- `claudeagent/sessions`: claude's transcripts on disk: list, details, messages, subagents, queued prompts, fork (whole or up to a message) and delete. Ported from the Claude Agent SDK for Python.
- `claudeagent/claudetest`: a scripted fake claude and cassettes of recorded runs, for tests with no process or login; `fakeapi`, a fake Messages API, and the recording tools under `cmd`.
- `claudeacp`: an ACP agent on claudeagent with claude-agent-acp's wire shape: sessions (new, load, resume, fork, list, delete, close), prompt queueing and steering, cancel, permissions with "always allow", modes and config options (model, effort, fast mode, agent), plans, AskUserQuestion as a form, MCP servers from the client, subagents as sessions of their own, notices, slash commands, usage and context window, session titles.
- `cmd/claude-acp`: the agent as a program, for Zed and other ACP clients.
